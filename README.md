# call me maybe

## Description

This project implements a **function calling system** for Large Language Models: given a natural-language prompt (e.g. *"What is the sum of 2 and 3?"*), the program identifies which function should be called and extracts the correctly-typed arguments for it (e.g. `fn_add_numbers` with `{"a": 2, "b": 3}`), instead of answering the question directly in plain text.

The core challenge is that small language models (here, `Qwen/Qwen3-0.6B`, ~0.6B parameters) are unreliable at spontaneously producing well-structured output. This project solves that with **constrained decoding**: rather than hoping the model produces a valid function name and valid, correctly-typed argument values, the generation process is guided token-by-token so that only tokens consistent with the expected schema can ever be selected. This guarantees, by construction, that every generated function name is a real function and every generated value is syntactically valid for its declared type.

The JSON structure of the final output (keys, braces, commas) is built in Python, not generated by the model — only the two things that actually require language understanding are delegated to the LLM: **which function to call**, and **what value each parameter should take**.

## Algorithm Explanation

The generation process happens in two phases per prompt, both driven by a finite-state machine (`JSONStateMachine`) that tracks what is currently "valid" and filters the model's vocabulary accordingly.

### 1. Function selection

- The model is given the user's prompt and a textual list of the available functions (name, description, parameter names).
- Tokens are generated one at a time. At each step, `JSONStateMachine.valid_function_token` checks whether the text accumulated so far, plus the candidate token, is still a **prefix** of at least one real function name.
- Only the highest-scoring token among the *valid* ones is kept; every invalid token is effectively assigned a probability of zero for this step, exactly like setting its logit to `-inf` before sampling.
- Selection stops as soon as the accumulated text matches exactly **one** function name and no other function name extends it further (this avoids stopping early on `fn_add` when `fn_add_numbers` also exists).

### 2. Value generation (per parameter)

Once the function is known, its parameters are known too (`functions_definition.json` defines their order and types) — so the model is **not** asked to choose which parameter to fill next; Python iterates over them in schema order and asks the model to generate a value for each, prompted with the user request, the chosen function, and the values generated so far.

Each parameter type has its own constraint:
- **`string`**: the model must first emit a token that is a literal `"`. Every subsequent token is accepted as part of the string until another literal `"` closes it.
- **`number`**: tokens are accepted as long as the accumulated text still matches a valid (possibly incomplete) numeric pattern (`-?\d*\.?\d*`). The value is considered complete once the text is a fully valid number (`-?\d+(\.\d+)?`) and a whitespace-like delimiter token follows.
- **`boolean`**: tokens are accepted as long as they are a prefix of `"true"` or `"false"`; completion happens on an exact match.

### Handling premature termination

Not every parameter type has a clean, explicit closing token generated by the model. Numbers and booleans have no equivalent of the closing `"` used for strings, and a 0.6B model isn't reliable about spontaneously emitting a delimiter after them. Two safeguards handle this:

- `is_forced_complete()`: if no valid continuation token exists at all, but the text accumulated so far is already a syntactically complete number or boolean, generation stops instead of raising an error.
- `should_stop_early()`: before even attempting constrained selection, if the value is already complete *and* the model's own top, **unconstrained** choice would not extend it further, generation stops. This was added after observing that a constrained-but-unbounded numeric pattern can otherwise keep accepting "technically valid" digits indefinitely, well past the point where the model intended to stop (see Challenges Faced).

## Design Decisions

- **JSON structure is built in Python, not by the LLM.** The subject's own example (`{"function": "add_numbers", "arguments": {...}}`) frames the model's job as *deciding* the function and *extracting* arguments — not typesetting punctuation. Delegating `{`, `"`, `:`, `,`, `}` to Python keeps the model's role focused on the part that actually needs language understanding, and removes an entire class of failure modes (mismatched braces, stray commas) from the constrained decoding problem.
- **Parameters are filled in schema order, not chosen by the model.** Since `functions_definition.json` already declares each function's parameter names and types, there is nothing for the model to "decide" about which parameter comes next — only what value it should take. This removed an entire (unnecessary) state from the state machine.
- **Greedy, highest-valid-logit token selection.** At each step, `get_next_token` scans tokens from highest to lowest logit and returns the first one that the state machine accepts. This is a straightforward extension of greedy decoding, restricted to a validity mask, rather than a full beam search — simpler to reason about and fast enough for prompts of this size.
- **Separate exception types per failure mode** (`FunctionSelectionError`, `ValueGenerationError`, `NoValidTokenError`) so that failures are diagnosable (which phase failed, for which prompt) and so `main.py` can catch them precisely at the per-prompt level.

## Performance Analysis

- Speed: 5  minutes to process the full test set with `make run`, and less than 30 seconds per prompt
- Reliability: 90% of successfully-generated outputs are valid, schema-compliant JSON (guaranteed by construction, not just observed)

## Challenges Faced


- **State not persisted after constrained token selection.** An early version of `get_next_token` validated each candidate token against a *copy* of the state machine (to safely test multiple candidates without mutating state on failed attempts), but never propagated the accepted token's state change back to the real state machine object once a valid token was found. This meant flags like `function_complete` never actually became `True`, and the generation loop would run for its full token budget every time without detecting completion. Fixed by syncing the real state machine's state from the successful candidate copy before returning.
- **Unbounded numeric generation.** Because the constraint for `number` values accepts any digit-continuation token without a maximum length, and `get_next_token` always picks the highest-scoring *valid* token, a digit token could keep winning over a whitespace/delimiter token turn after turn — especially since this 0.6B model isn't fine-tuned for this task and can drift into unrelated text containing more digits. This caused value generation to exhaust its token budget without ever terminating. Fixed with `should_stop_early`, which checks the model's own unconstrained top choice once a value is already syntactically complete, and stops there instead of continuing to force digits that are merely lexically valid.

## Testing Strategy

- Manual runs against the provided `function_calling_tests.json` covering all five functions (`fn_add_numbers`, `fn_greet`, `fn_reverse_string`, `fn_get_square_root`, `fn_substitute_string_with_regex`), across `number`, `string`, and multi-parameter cases.
- Inspection of `data/output/function_calling_results.json` after each run to confirm valid JSON, correct function names, correct argument types, and complete parameter sets.
