# Call Me Maybe — function calling with constrained decoding

[![CI](https://github.com/imyassmine/call-me-maybe/actions/workflows/ci.yml/badge.svg)](https://github.com/imyassmine/call-me-maybe/actions/workflows/ci.yml)

[![Managed with uv](https://img.shields.io/badge/managed%20with-uv-261230.svg)](https://docs.astral.sh/uv/)
[![Lint: flake8](https://img.shields.io/badge/lint-flake8-informational.svg)](https://flake8.pycqa.org/)
[![Types: mypy](https://img.shields.io/badge/types-mypy-checked-blue.svg)](https://mypy-lang.org/)

A **function-calling system for small language models**. Given a natural-language
request such as *"What is the sum of 2 and 3?"*, the program decides which function
should be called and extracts the correctly-typed arguments (`fn_add_numbers` with
`{"a": 2, "b": 3}`) instead of answering in plain text.

Instead of hoping that a 0.6 B-parameter model emits valid structured output, the
generation is **constrained token by token with a finite-state machine**, so invalid
function names and malformed argument values are impossible by construction — no
fine-tuning required.

> Built as part of the [42](https://42.fr/) curriculum's function-calling activity by
> **Yassmine Abdallah** ([@imyassmine](https://github.com/imyassmine)).

## Demo

Actual output on the provided fixtures ([Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B),
CPU, no GPU):

| Prompt | Generated call |
| --- | --- |
| `What is the sum of 2 and 3?` | `fn_add_numbers(a=2, b=3)` |
| `Greet shrek` | `fn_greet(name="Shrek")` |
| `Reverse the string 'hello'` | `fn_reverse_string(s="hello")` |
| `What is the square root of 16?` | `fn_get_square_root(a=16)` |
| `Substitute the word 'cat' with 'dog' in 'The cat sat on the mat with another cat'` | `fn_substitute_string_with_regex(source_string="The cat sat on the mat with another cat", regex="cat", replacement="dog")` |

The JSON envelope (keys, braces, commas) is never generated by the model: only the
two decisions that actually require language understanding — **which function** and
**which value per parameter** — are delegated to the LLM.

## Why this project

The interesting part of function calling is not calling `json.loads`. Small models
are unreliable at spontaneously producing well-structured output: they drift,
hallucinate function names, or emit arguments of the wrong type. Prompting harder
does not fix that.

This project flips the problem around: rather than generating free text and hoping
it parses, the **decoder itself is constrained** by the function schema. At every
step, the model's vocabulary is filtered to the tokens that keep the output valid,
and the highest-scoring remaining token is selected. That is the same idea used by
grammar-constrained generation tools such as Outlines and `llama.cpp` grammars,
implemented here from scratch to understand it end to end.

What that buys:

- function names are guaranteed to be declared functions, never hallucinated;
- argument syntax is guaranteed valid for its declared JSON type;
- the output is a real Python object with `int` / `float` / `str` / `bool` values —
  no string post-processing of the model's text;
- the approach works on a CPU-only 0.6 B model, with no fine-tuning.

## How it works

```
                        user prompt
                             │
                             ▼
        ┌──────────────────────────────────────┐
        │ 1. Function selection                │
        │    constrained token by token to     │
        │    prefixes of real function names   │
        └───────────────────┬──────────────────┘
                            │ chosen FunctionDefinition
                            ▼
        ┌──────────────────────────────────────┐
        │ 2. Value generation, per parameter   │
        │    constrained by the declared type  │
        │    (number / string / boolean)       │
        └───────────────────┬──────────────────┘
                            │ raw, type-checked values
                            ▼
        ┌──────────────────────────────────────┐
        │ 3. Python assembles the final call   │
        │    {"prompt", "name", "parameters"}  │
        └──────────────────────────────────────┘
```

### 1. Function selection

The model is given the user's prompt and a textual list of the available functions
(name, description, parameter names). Tokens are generated one at a time. At each
step, `JSONStateMachine.valid_function_token` checks whether the text accumulated so
far, plus the candidate token, is still a **prefix** of at least one real function
name.

Only the highest-scoring token among the *valid* ones is kept; every invalid token is
effectively assigned a probability of zero for this step — exactly like setting its
logit to `-inf` before sampling. Selection stops as soon as the accumulated text
matches exactly **one** function name and no other function name extends it further
(this avoids stopping early on `fn_add` when `fn_add_numbers` also exists).

### 2. Value generation (per parameter)

Once the function is known, its parameters are known too
(`functions_definition.json` defines their order and types), so the model is **not**
asked to choose which parameter to fill next: Python iterates over them in schema
order and asks the model for a value, prompted with the user request, the chosen
function, and the values generated so far.

Each parameter type gets its own constraint:

| JSON type | Constraint on the generated text |
| --- | --- |
| `string` | the model must first emit a literal `"`; every token is accepted until another literal `"` closes the value |
| `number` | tokens are accepted while the text matches `-?\d*\.?\d*`; the value completes once it matches `-?\d+(\.\d+)?` and a whitespace delimiter follows |
| `boolean` | tokens must remain a prefix of `"true"` or `"false"`; completion happens on the exact match |

### Handling premature termination

Not every type has a clean closing token. Numbers and booleans have no equivalent of
the closing `"` used for strings, and a 0.6 B model is not reliable about
spontaneously emitting a delimiter. Two safeguards handle that:

- `is_forced_complete()`: if no valid continuation token exists at all, but the text
  accumulated so far is already a syntactically complete number or boolean,
  generation stops instead of raising an error.
- `should_stop_early()`: before attempting constrained selection, if the value is
  already complete *and* the model's own top, **unconstrained** choice would not
  extend it further, generation stops. This was added after observing that a
  constrained-but-unbounded numeric pattern can otherwise keep accepting
  "technically valid" digits indefinitely, well past the point where the model
  intended to stop (see [Challenges faced](#challenges-faced)).

## Design decisions

- **JSON structure is built in Python, not by the LLM.** The task frames the model's
  job as *deciding* the function and *extracting* arguments — not typesetting
  punctuation. Delegating `{`, `"`, `:`, `,` and `}` to Python keeps the model's role
  focused on the part that actually needs language understanding, and removes an
  entire class of failure modes (mismatched braces, stray commas) from the
  constrained-decoding problem.
- **Parameters are filled in schema order, not chosen by the model.** Since
  `functions_definition.json` already declares each function's parameter names and
  types, there is nothing for the model to "decide" about which parameter comes
  next — only what value it should take. This removed an entire (unnecessary) state
  from the state machine.
- **Greedy, highest-valid-logit token selection.** At each step, `get_next_token`
  scans tokens from highest to lowest logit and returns the first one that the state
  machine accepts. This is a straightforward extension of greedy decoding,
  restricted to a validity mask, rather than a full beam search — simpler to reason
  about and fast enough for prompts of this size.
- **One exception type per failure mode** (`FunctionSelectionError`,
  `ValueGenerationError`, `NoValidTokenError`) so that failures are diagnosable
  (which phase failed, for which prompt) and so `__main__.py` can catch them
  precisely at the per-prompt level.
- **Pydantic models for every file boundary.** Function definitions and prompt
  fixtures are validated on load, so a malformed input file fails loudly with a
  useful message instead of producing a confusing downstream error.

## Results and performance

- **Test set:** all 11 prompts of `function_calling_tests.json` are processed
  successfully and produce schema-compliant output — the structural validity is a
  property of the decoder, not a lucky observation.
- **Semantic quality:** on a manual review of the reference run, 9 of the 11 calls
  also had semantically correct argument values; the two imperfect calls are both
  regex substitutions, where the 0.6 B model produces approximate regexes
  (for example a pattern of `34,233` instead of `\d+`). See
  [Limitations](#limitations-and-next-steps).
- **Speed:** a few minutes (≈5 min) for the full 11-prompt set on a 4-core CPU with
  no GPU; under ~30 s per prompt once the model is loaded.
- **Validation tooling:** `scripts/verify_results.py` re-checks every generated call
  against the function schema (structure, known names, exact parameter set, JSON
  value types).

## Project structure

```
.
├── src/                          # implementation
│   ├── __main__.py               # CLI, model loading, per-prompt orchestration
│   ├── generate.py               # two-phase generation + Python type conversion
│   ├── state_machine.py          # constrained-decoding finite-state machine
│   ├── token_selection.py        # highest-valid-logit selection, early stopping
│   ├── prompts.py                # prompt templates
│   └── json_file_parsing.py      # Pydantic models + JSON fixture loading
├── llm_sdk/                      # inference SDK provided with the 42 activity
│   └── llm_sdk/__init__.py       # small wrapper around transformers
├── data/input/                   # function schema and prompt fixtures
├── scripts/
│   └── verify_results.py         # validates generated calls against the schema
├── tests/                        # offline unit tests (no model download)
├── .github/workflows/            # CI + manual model smoke test
├── Makefile                      # developer shortcuts
├── pyproject.toml                # dependencies, dev tools, pytest/mypy config
└── uv.lock                       # fully pinned dependency graph
```

> `llm_sdk/` is the inference wrapper supplied with the activity: a thin
> `transformers`-based class that loads the model, tokenizes and exposes raw logits.
> It is imported from the repository root, so run every command from the project
> root (as the Makefile and CI do).

## Quick start

### Requirements

- Python 3.10+
- [uv](https://docs.astral.sh/uv/) (dependency and virtualenv manager)
- ~2 GB of disk for the dependencies, plus ~1.5 GB for the model on first run

### Installation and run

```bash
git clone https://github.com/imyassmine/call-me-maybe.git
cd call-me-maybe

make install   # uv sync: creates .venv, installs deps + dev tools
make run       # runs the model on the provided fixtures
```

The first `make run` downloads `Qwen/Qwen3-0.6B` from the Hugging Face Hub and caches
it in `~/.cache/huggingface/`; later runs start instantly. Results are written to
`data/output/function_calling_results.json` (git-ignored).

Run with custom files:

```bash
make run ARGS="--input my_prompts.json --output my_results.json"
```

or call the module directly:

```bash
uv run python -m src \
  --functions_definition data/input/functions_definition.json \
  --input data/input/function_calling_tests.json \
  --output data/output/function_calling_results.json
```

### Make targets

| Target | Description |
| --- | --- |
| `make install` | Install dependencies and dev tools with `uv sync` |
| `make run` | Run the function-calling tool (`ARGS="..."` to pass CLI options) |
| `make debug` | Run the main module under `pdb` |
| `make lint` | `flake8` + `mypy` |
| `make lint-strict` | `mypy --strict` (in addition to `flake8`) |
| `make test` | Run the offline unit test suite with `pytest` |
| `make clean` | Remove compiled files and caches |
| `make help` | List the available targets |

## Input and output formats

**Function definitions** (`data/input/functions_definition.json`) — a JSON array of
functions; parameter order is meaningful and types drive the decoder:

```json
[
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {
      "a": { "type": "number" },
      "b": { "type": "number" }
    },
    "returns": { "type": "number" }
  }
]
```

**Prompts** (`data/input/function_calling_tests.json`):

```json
[{ "prompt": "What is the sum of 2 and 3?" }]
```

**Generated results** (`data/output/function_calling_results.json`):

```json
[
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": { "a": 2, "b": 3 }
  }
]
```

Supported parameter types: `number` (`int` / `float`), `string`, `boolean`.

Check any results file against the schema:

```bash
make run
uv run python scripts/verify_results.py
# ✓ 11 call(s) valid and schema-compliant in data/output/function_calling_results.json
```

## Testing and CI

The repository ships an **offline unit test suite** (41 tests) covering the state
machine, token selection, prompt building, fixture validation and value conversion.
The tests need neither a GPU nor a model download, so they run in a few seconds:

```bash
make test
```

Quality gates, run locally and in CI:

```bash
make lint         # flake8 + mypy
make lint-strict  # mypy --strict
```

GitHub Actions ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs on every
push and pull request to `main`:

1. installs the pinned environment with `uv sync --frozen` (Python 3.10),
2. runs `flake8`,
3. runs `mypy`,
4. runs the unit test suite.

A second, **manually triggered** workflow
([`.github/workflows/model-smoke-test.yml`](.github/workflows/model-smoke-test.yml))
runs the real Qwen3-0.6B model on the provided prompts, validates the output with
`scripts/verify_results.py`, and uploads the results as an artifact. It is manual
because it downloads ~1.5 GB and takes several minutes — too heavy for every push.

## Limitations and next steps

Honest boundaries of the current implementation:

- **Semantic accuracy is bounded by the model.** Constrained decoding guarantees
  structure and types, not meaning: the 0.6 B model produces plausible but
  approximate regex arguments. A larger model or few-shot examples in the prompt
  would improve that.
- **Greedy decoding only.** No beam search, sampling or self-consistency; adding a
  re-ranking pass is a natural extension.
- **Sequential prompts, no batching.** Prompts are processed one at a time; batching
  and KV-cache reuse would make the tool substantially faster.
- **Only three JSON types** (`number`, `string`, `boolean`) are supported. Enums,
  arrays and nested objects would be the next step for the state machine.
- **No retry strategy.** A failed prompt is skipped and reported; a retry with a
  different prompt template could recover some of them.
- **`llm_sdk/` is vendored** rather than published as a dependency; extracting it
  into its own package would make the repository cleaner.

## Challenges faced

- **State not persisted after constrained token selection.** An early version of
  `get_next_token` validated each candidate token against a *copy* of the state
  machine (to safely test multiple candidates without mutating state on failed
  attempts), but never propagated the accepted token's state change back to the real
  state machine object once a valid token was found. This meant flags like
  `function_complete` never actually became `True`, and the generation loop would run
  for its full token budget every time without detecting completion. Fixed by syncing
  the real state machine's state from the successful candidate copy before returning.
- **Unbounded numeric generation.** Because the constraint for `number` values accepts
  any digit-continuation token without a maximum length, and `get_next_token` always
  picks the highest-scoring *valid* token, a digit token could keep winning over a
  whitespace/delimiter token turn after turn — especially since this 0.6 B model is
  not fine-tuned for this task and can drift into unrelated text containing more
  digits. This caused value generation to exhaust its token budget without ever
  terminating. Fixed with `should_stop_early`, which checks the model's own
  unconstrained top choice once a value is already syntactically complete, and stops
  there instead of continuing to force digits that are merely lexically valid.
